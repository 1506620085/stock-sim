# 多用户功能开发规划

## 1. 文档目的

当前 `stock-sim` 是**单租户个人训练应用**：后端无登录、无 `User` 模型、业务表无 `user_id`；自选、复盘会话、买卖、笔记、费率等在 PostgreSQL 中全局共享，偏好与部分 UI 状态在浏览器 `localStorage`。

本文规划**新增多用户能力**时的目标边界、技术选项、数据归属与推荐开发顺序，作为后续设计与排期依据。实现前应先确认产品形态（见第 3 节），再按阶段落地。

相关现状文档：

- [设计文档.md](./设计文档.md)
- [开发内容顺序.md](./开发内容顺序.md)

---

## 2. 现状摘要（与多用户相关）

| 维度 | 现状 | 多用户影响 |
| --- | --- | --- |
| 认证 | 无 JWT / Cookie 登录 / OAuth | 必须新增用户与鉴权 |
| 用户模型 | 无 | 新增 `users`（及可选 `sessions`） |
| 业务数据 | 全局共享，无所有者 | 几乎都需按用户隔离 |
| 行情主数据 | `instruments` / `kline_daily` 全局 | **可继续共享**，不必按用户复制 |
| 偏好设置 | 前端 `localStorage` | 建议迁库或按用户命名空间 |
| API 客户端 | `apiFetch` 无鉴权头 | 需统一注入 Token / Cookie |
| 部署 | 本机 Vite + Uvicorn + Compose Postgres | 多用户后需 HTTPS、密钥、备份与限流 |

**可继续共享（全局）的数据：**

- 标的字典、日 K、行情同步任务结果

**必须按用户隔离的数据：**

- 自选、复盘会话、买卖、区间复盘、笔记/交易规则、费率模板（或用户覆盖）
- 账户初始资金、结算调整、统计口径相关偏好
- 活跃会话、图表/标签等 UI 偏好（库内或按用户 key）

## 3. 产品形态先定（影响整条路线）

在写代码前，先从下面选一条主路径（可演进，但第一期只选一个）。

### 方案 A：个人多设备同步（推荐作为第一期）

- 少量账号（家人/自己多端），每人独立数据
- 本地或私有部署，不一定要公开注册
- 目标：换电脑、手机浏览器不丢复盘与笔记

### 方案 B：小团队 / 训练营

- 管理员开户，学员各自训练
- 可选：管理员只读学员统计（第二期再做）
- 目标：隔离数据 + 简单角色

### 方案 C：公开 SaaS

- 自助注册、找回密码、计费、滥用防护、多租户运维
- 工作量和合规成本明显高于 A/B，**不建议在现有功能未稳定前直接上**

**建议：** 第一期按 **方案 A** 做「注册/登录 + 数据按用户隔离 + 偏好上云」；预留角色字段，方便以后扩到 B。

## 4. 技术选项对比

### 4.1 认证与会话

| 选项 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **JWT（Access + Refresh）+ HttpOnly Cookie** | 前后端分离常见；Refresh 可吊销；Cookie 减 XSS 偷 Token | 需 CSRF 防护（SameSite）与密钥轮换 | **推荐默认** |
| JWT 放 `Authorization: Bearer` | 实现简单、易调 | XSS 风险更高；移动/多端要自己管存储 | 内网原型可暂用 |
| 服务端 Session（Redis/DB） | 吊销简单、模型直观 | 要 Session 存储与粘性/共享 | 更偏传统站点 |
| Authlib / OAuth2（GitHub 等） | 少记密码 | 依赖第三方；个人部署不一定需要 | 第二期可选登录方式 |
| 完整 IdP（Keycloak / Auth0 / Clerk） | 省自研 | 成本与运维重；与当前体量不匹配 | SaaS 再考虑 |

**密码存储：** `argon2` 或 `bcrypt`（推荐 argon2）。  
**库建议：** FastAPI 生态可用 `pwdlib` / `passlib`（注意维护状态）、`PyJWT` 或 `python-jose`；Refresh Token 落库便于登出与吊销。

### 4.2 授权与用户上下文

| 选项 | 说明 |
| --- | --- |
| **FastAPI `Depends(get_current_user)`** | 所有业务路由统一注入；**推荐** |
| 中间件写 `request.state.user` | 也可，但 Depends 更易测、类型更清晰 |
| Row Level Security（Postgres RLS） | 强隔离，但与 SQLModel 叠加复杂；可作后期加固，**第一期不必** |

### 4.3 数据隔离模型

| 选项 | 说明 | 建议 |
| --- | --- | --- |
| **每业务表加 `user_id` FK** | 实现直接，查询一律带 `user_id=` | **第一期采用** |
| 多 schema / 多库 per tenant | 隔离强，运维重 | 不做 |
| 组织（org）+ 成员 | 适合团队空间 | 预留 `org_id` 字段可选，第一期可只用 `user_id` |

### 4.4 前端鉴权

| 选项 | 说明 |
| --- | --- |
| 登录页 + 受保护路由 | `App.tsx` 增加未登录重定向；或引入 React Router |
| `apiFetch` 自动带 Cookie / 401 跳转登录 | **必须** |
| 用户偏好从 API 拉取，弱化 localStorage | 多设备一致；本地可作缓存 |

### 4.5 注册与安全基线（第一期最小集）

- 邮箱或用户名 + 密码注册（可配置关闭公开注册，改「仅管理员开户」）
- 登录失败限流、密码强度规则
- HTTPS（对外暴露时）
- CORS 收紧为真实前端源，且 `credentials: true` 时与 Cookie 方案一致
- 敏感配置只放环境变量（`JWT_SECRET`、`DATABASE_URL`）

### 4.6 不推荐第一期引入的技术

- 微服务拆分认证服务
- 复杂权限引擎（Casbin 等）——先用 `role: user | admin` 枚举即可
- 为多用户单独换数据库（继续 PostgreSQL）

## 5. 目标数据模型（草案）

```text
users
  id, email/username, password_hash, role, is_active, created_at, updated_at

auth_refresh_tokens（可选但推荐）
  id, user_id, token_hash, expires_at, revoked_at, user_agent, created_at

# 以下表增加 user_id（非空）+ 索引 (user_id, ...)
watchlist_items
replay_sessions
trades              # 也可仅通过 session 归属推导，但建议冗余 user_id 便于统计查询
trade_reviews
journal_entries
trading_rules
fee_templates       # 或：系统模板全局 + 用户自定义带 user_id

user_preferences    # 替代/同步 localStorage 中的资金、复权、成交价规则等
  user_id UNIQUE, payload JSONB, updated_at
```

**唯一约束调整示例：**

- 自选：由「全局 `instrument_id` 唯一」改为「`(user_id, instrument_id)` 唯一」
- 费率默认：按 `user_id + asset_type` 设置默认模板

**行情表不变：** `instruments`、`kline_daily` 仍全局共享；同步任务继续系统级。

## 6. API 与前端改造要点

### 6.1 后端

新增例如：

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `POST /api/auth/refresh`
- `GET  /api/auth/me`
- `GET/PUT /api/me/preferences`

改造原则：

1. 所有用户业务路由：`Depends(get_current_user)`。
2. 列表/详情/更新/删除：**先校验资源 `user_id == current_user.id`**，禁止仅凭资源 id 操作。
3. `/api/account/reset`、统计接口：只作用于当前用户。
4. 健康检查、行情同步（若保留手动触发）可继续公开或仅 admin。

### 6.2 前端

1. 登录 / 注册页与「未登录不可进复盘」门禁。
2. `api/client.ts`：Cookie 模式设 `credentials: "include"`；401 清状态并跳转登录。
3. 启动时 `GET /api/auth/me` + 拉取 preferences，再灌入现有设置逻辑。
4. localStorage key 增加 `userId` 前缀作过渡，或逐步废弃跨用户串数据。
5. 导航区展示当前用户与退出。

## 7. 推荐开发顺序（分阶段）

整体原则：**先身份，再隔离，再迁移存量，再体验，最后增强**。每一阶段结束应可演示、可回滚迁移。

### 阶段 0：定案与基线（0.5～1 天）

- 确认产品形态 A/B/C、是否开放注册、是否要邮箱验证。
- 约定 Cookie 域名、本地与生产 CORS、密钥管理。
- 在设计文档中补「用户与权限」一节（可链到本文）。

**产出：** 决策记录（形态、登录方式、是否开放注册）。

---

### 阶段 1：用户与认证骨架（优先）

**后端**

1. `User` 模型 + Alembic 迁移。
2. 注册 / 登录 / 登出 / me；密码哈希；JWT 或 Session 落地。
3. `get_current_user` 依赖；用 1～2 个受保护的探活接口验证。
4. 单测：注册、错误密码、受保护路由 401。

**前端**

1. 登录页 UI（风格贴合现有设置页，避免另起一套视觉）。
2. `apiFetch` 鉴权与 401 处理。
3. 启动鉴权门禁。

**验收：** 无 Token 访问业务 API 返回 401；登录后 `me` 正常。

---

### 阶段 2：数据模型加 `user_id`（核心）

顺序建议（依赖从浅到深）：

1. `user_preferences`（新表，压力小）
2. `watchlist_items`
3. `fee_templates`（若保留全局系统模板，则拆「系统 / 用户」）
4. `replay_sessions`
5. `trades` / `trade_reviews`（随 session 或显式 `user_id`）
6. `journal_entries` / `trading_rules`

每张表：

- 迁移加列 → 回填策略（见阶段 3）→ 改唯一索引 → 改 CRUD 过滤 → 测越权（用户 A 不能读写 B）。

**验收：** 两个测试账号数据互不可见；行情同步仍全局可用。

---

### 阶段 3：存量单租户数据迁移

现有库通常已有「一个人」的数据，需要一次性归属策略：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| **指定所有者**（推荐） | 迁移时创建环境变量/种子创建首个 admin，把旧行 `user_id` 全部指给该用户 | 个人项目升级 |
| 清空业务表 | 只保留行情，训练数据作废 | 可接受重来时 |
| 导出备份后清空 | `pg_dump` 后再迁移 | 更稳妥 |

**注意：** 迁移脚本要可重复执行或明确「只跑一次」；上线前备份。

**验收：** 旧复盘会话、买卖、笔记在首个账号下仍可打开；第二账号为空。

---

### 阶段 4：业务 API 全面鉴权与前端联调

1. 自选、复盘、交易、统计、笔记、设置中的费率接口全部挂用户上下文。
2. 前端去掉「裸调 API 假设全局唯一」的逻辑（例如默认拉「最新会话」时必须带当前用户）。
3. 账户重置、Excel 导入导出仅限本人会话。
4. 回归主路径：自选 → 复盘买卖 → 区间复盘 → 统计 → 笔记。

**验收：** 双账号并行操作无串数据；主路径 E2E 或手工清单通过。

---

### 阶段 5：偏好与本地状态上云

1. 将 `stock-sim.preferences`、费率偏好等写入 `user_preferences`。
2. 登录后拉取覆盖本地；变更防抖写回 API。
3. 活跃复盘会话 id、主图指标等：优先服务端，或 `localStorage` key 带 `userId`。

**验收：** 同账号两浏览器偏好一致；换账号不串偏好。

---

### 阶段 6：安全与运营加固

1. 登录/注册限流；锁定策略（可选）。
2. Admin：禁用用户、重置密码、关闭公开注册。
3. 审计日志（登录成功/失败、重置账户）——可选。
4. Compose / 部署文档补充 HTTPS、密钥、备份。
5. 基础监控：5xx、登录失败率。

**验收：** 暴力尝试被限；admin 可禁用账号。

---

### 阶段 7（可选增强）

按需排序，勿阻塞主路径：

1. 邮箱验证 / 忘记密码
2. OAuth 第三方登录
3. 角色：讲师查看学员统计（只读授权）
4. 组织空间、邀请链接
5. Postgres RLS 加固
6. 多设备 Refresh Token 管理（设备列表、一键下线）

## 8. 建议里程碑与工作量（粗估）

| 里程碑 | 内容 | 粗估（一人） |
| --- | --- | --- |
| M1 | 阶段 0～1 认证可用 | 2～4 天 |
| M2 | 阶段 2～3 隔离 + 存量归属 | 4～8 天 |
| M3 | 阶段 4 全业务联调 | 3～6 天 |
| M4 | 阶段 5～6 偏好同步与安全 | 2～4 天 |

合计约 **2～4 周**（视测试覆盖与历史数据复杂度浮动）。方案 C（公开 SaaS）需另加注册防刷、邮件、合规与运维，再翻倍以上。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 漏改某个列表接口导致串数据 | 统一 Repository/查询助手强制 `user_id`；加「越权」集成测试 |
| 迁移把旧数据弄丢 | 先 `pg_dump`；迁移可 dry-run；首用户归属策略写进脚本注释 |
| Cookie 跨域本地联调失败 | 本地同站点反代，或明确 Vite proxy + SameSite 配置 |
| localStorage 残留串号 | key 带 userId；退出时清理 |
| JWT 密钥泄露 | 环境变量、轮换、Refresh 可吊销 |
| 范围膨胀到 SaaS | 第一期书面锁定方案 A，增强进阶段 7 |

## 10. 推荐技术栈（第一期冻结建议）

在现有栈上增量，避免平行重写：

```text
后端：FastAPI + SQLModel + Alembic + PostgreSQL（已有）
认证：密码 argon2 + JWT Access（短时）+ Refresh（HttpOnly Cookie，落库可吊销）
授权：Depends(get_current_user) + 行级 user_id 过滤
前端：现有 React/Vite；登录页 + apiFetch credentials；偏好 API 化
部署：继续 Docker Compose Postgres；对外时 Nginx HTTPS
```

**明确不做（第一期）：** 多租户分库、Keycloak、微服务拆分、RLS、计费。

## 11. 验收清单（多用户第一期 Definition of Done）

- [ ] 可注册/登录/退出；未登录无法使用业务 API
- [ ] 至少两个用户，自选/复盘/买卖/笔记/统计互不可见
- [ ] 历史单租户数据已归属到指定首个用户（或已确认清空）
- [ ] 行情数据仍共享，同步不必每用户一份
- [ ] 偏好多设备基本一致（或已文档说明仅部分上云）
- [ ] 越权访问返回 403/404（不泄露资源是否存在的策略需统一）
- [ ] 文档：环境变量、迁移步骤、开户方式已更新
