## 1. 文档目的与现状

当前 `stock-sim` 仍是**单租户个人训练应用**：

| 维度 | 现状 |
| --- | --- |
| 认证 | 无登录 / 无 JWT / Cookie |
| 用户 | 无 `User` 模型 |
| 业务数据 | PostgreSQL 中全局共享，无 `user_id` |
| 行情主数据 | `instruments` / `kline_daily` 全局（多用户后仍可共享） |
| 偏好 | 大量依赖浏览器 `localStorage` |
| 训练模式 | 以「自选 + 指定复盘会话」为主；**尚无随机训练模式** |

## 2. 待办备忘（产品向）

### 2.1 随机训练模式（看情况是否新表）

**意图：** 类似 iPad 类股票训练软件——**随机股票、随机 K 线位置**，用户在未知标的/未知时间轴的前提下练习买卖。

**当前判断：**

- 现有 `replay_sessions` 偏「用户自选标的 + 自选复盘日」的主动复盘，和「随机开局」模型不完全相同。
- **有较大概率需要新表（或明确扩展会话类型）**，例如：

```text
# 名称待定，示意 only
training_runs / random_training_sessions
  id
  user_id
  instrument_id          -- 对用户可先隐藏，结算或结束后再揭示
  start_trade_date       -- 随机落点
  visible_bars_before    -- 开局可见历史深度等
  status                 -- active / finished / abandoned
  reveal_at / revealed   -- 是否已揭晓真实标的与日期
  score / summary JSONB  -- 成绩与复盘摘要（后续）
  created_at, updated_at
```

- 也可能在 `replay_sessions` 上增加 `mode: manual | random` + 随机元数据 JSONB；**是否独立成表，等详细功能设计时再定**。
- 可能遇见问题：因为是随机股票所以要获取所有股票的代码与名称，若要这样，就只获取代码与名称，不获取K线内容，即类似懒加载，不点进去不进行获取K线图加载，随机也是，不随机到就不下载内容K线图内容，若下载了就跟复盘一样，保存好，以便下次直接使用

**本阶段约定：**

- 只记需求与表结构备选，**不阻塞**登录/多用户主线。
- 详细玩法（揭晓时机、评分、排行、与现有买卖/笔记如何复用）**后续再开发**。

### 2.2 登录页与免登录时长

**新增登录页**（未登录不可进业务页，或可浏览有限公开页——第一期建议业务全门禁）。

**「保持登录 / 免登录」选项（Refresh 有效期）：**

| 选项 | 建议 Refresh 有效期 | 说明 |
| --- | --- | --- |
| 1 天 | 24h | 公共电脑 |
| 7 天 | 7d | 默认推荐之一 |
| 30 天 | 30d | 个人设备 |
| 半年 | 182d | 长期设备 |
| 永久 | 很长或「直到主动登出」 | 需可吊销；实际仍建议设上限（如 400d）并支持服务端踢下线 |

实现要点：

- Access Token 仍宜**短时**（如 15～30 分钟）。
- 「免登录」只拉长 **Refresh Token** 过期时间，并落库便于吊销。
- 登录表单勾选/单选上述时长，写入 refresh 记录的 `expires_at`。

---

### 2.3 新增用户功能

- 用户注册或管理员开户（第一期建议可配置：开放注册 / 仅管理员开户）。
- 用户资料：`email` 或 `username`、密码、角色（`user` / `admin`）、启用状态。
- 登录 / 登出 / 当前用户（`me`）。
- 后续可选：改密、禁用账号、设备列表与一键下线。

---

### 2.4 逐步按用户划分业务逻辑

**全局可继续共享：**

- `instruments`、`kline_daily`、系统级行情同步

**必须逐步挂 `user_id` 并鉴权过滤：**

- 自选、复盘会话、买卖、区间复盘、笔记/交易规则、费率模板（用户侧）
- 账户资金与结算、统计口径、偏好
- 未来的随机训练记录

原则：每张业务表改造时 **迁移 → 回填归属 → 改唯一约束 → CRUD 强制 `user_id` → 越权测试**，避免一次改爆。

## 3. 原开发顺序中仍有价值的阶段

> 摘自原 `开发内容顺序.md` 阶段 15 / 16 / 17+，作为未完成 backlog。

### 3.1 阶段 15：测试与稳定性（未系统完成）

目标：避免核心计算和数据同步出错。

建议覆盖：

- **后端单测：** FIFO 盈亏、最大浮亏、成交价规则、PostgreSQL upsert、Alembic 迁移
- **前端单测：** 计算器纯函数、关键表单/指标配置、菜单切换
- **E2E（Playwright 等）：** 自选 → 同步 K 线 → 复盘买卖 → 盈亏/笔记 → 统计

验收：核心计算有测试；一条完整复盘流程可自动化或清单化跑通。

---

### 3.2 阶段 16：打包与本地发布（未完成）

目标：稳定自用与可恢复。

建议：

- Docker Compose：PostgreSQL + API + Web（当前多为仅 DB）
- 前端构建托管策略（后端静态 或 独立 Web）
- Volume 持久化；`pg_dump` 备份与恢复脚本
- 交易/笔记导出（CSV / Markdown 等，可与现有 Excel 能力对齐）

验收：一键启动；重启数据仍在；能备份恢复。

---

### 3.3 阶段 17+：多用户 / 登录与数据隔离

即本文第 2、4、5、6 节；与随机训练表预留可并行设计、串行实现（先身份隔离，再训练模式）。

## 4. 技术选型（后续开发冻结建议）

在现有栈上增量，避免平行重写。

### 4.1 已采用（保持）

```text
前端：React + TypeScript + Vite + KLineCharts
后端：FastAPI + SQLModel/SQLAlchemy + Alembic
数据库：PostgreSQL
行情：AKShare 优先，Tushare 预留
部署：Docker Compose（Postgres 已有，全栈打包见阶段 16）
```

### 4.2 认证与会话（第一期推荐）

| 项 | 选型 |
| --- | --- |
| 密码 | `argon2`（或 bcrypt） |
| Access | JWT，短时 |
| Refresh | HttpOnly Cookie + **落库**（可吊销；写入用户选择的免登录时长） |
| 授权 | FastAPI `Depends(get_current_user)` |
| 隔离 | 业务表 `user_id` FK + 查询强制过滤（第一期不做 RLS / 分库） |

备选（不推荐第一期）：纯 Bearer 存 localStorage（XSS 风险）、完整 IdP（Keycloak/Auth0）。

### 4.3 前端鉴权

- 登录页 + 业务路由门禁（现有 `App.tsx` 手写路由可先加门禁；必要时再引 React Router）
- `apiFetch`：`credentials: "include"`，401 清状态并跳转登录
- 偏好逐步 API 化；过渡期 localStorage key 带 `userId`

### 4.4 明确第一期不做

- 公开 SaaS 计费、复杂权限引擎、认证微服务、Postgres RLS、为多用户换库
- 随机训练完整玩法（仅允许表结构/模式字段预留）

## 6. API 改造要点（多用户）

新增示例：

- `POST /api/auth/register`（可开关）
- `POST /api/auth/login`（body 含 `remember: 1d|7d|30d|182d|permanent`）
- `POST /api/auth/logout`
- `POST /api/auth/refresh`
- `GET  /api/auth/me`
- `GET/PUT /api/me/preferences`

原则：

1. 用户业务路由统一 `get_current_user`。
2. 读写前校验资源归属。
3. 账户重置、统计、导入导出仅当前用户。
4. 健康检查与系统级同步可公开或仅 admin。

## 7. 推荐开发流程顺序

整体原则：**先可测可发布基线 → 身份 → 隔离 → 存量归属 → 全业务鉴权 → 偏好上云 → 安全加固 →（可选）随机训练详设**。

| 顺序 | 阶段 | 内容 | 验收摘要 |
| --- | --- | --- | --- |
| 0 | 定案 | 产品形态（个人多设备 A / 小团队 B）；是否开放注册；旧数据归属 admin 还是清空 | 书面决策 |
| 1 | 阶段 15 可穿插 | 核心纯函数与关键 API 补测，避免多用户大改无回归网 | 关键路径有测试 |
| 2 | 认证骨架 | `User` + 登录页 + 免登录时长 + `apiFetch` 鉴权门禁 | 无 Token 业务 401；登录后 `me` 正常 |
| 3 | 表加 `user_id` | preferences → 自选 → 费率 → 会话 → 交易/复盘 → 笔记 | 双账号数据互不可见 |
| 4 | 存量迁移 | 旧行归属首个 admin（推荐）或清空业务表；先 `pg_dump` | 旧数据在首账号可打开 |
| 5 | 全业务联调 | 自选/复盘/统计/笔记/设置全部带用户上下文 | 双账号并行不串数据 |
| 6 | 偏好上云 | localStorage 关键项迁 `user_preferences` | 同账号多端基本一致 |
| 7 | 安全加固 | 登录限流、admin 禁用、密钥与 HTTPS 文档 | 暴力尝试受限 |
| 8 | 阶段 16 | Compose 全栈、备份恢复脚本 | 一键启动可恢复 |
| 9 | 随机训练（后续） | 定表或扩 session → 随机开局 → 揭晓与成绩 | 另开专题设计后再做 |

**分支建议：** `feat/multi-user-auth` 独立推进；勿与行情/图表大重构挤同一长期分支。

**粗估（一人，多用户 M1～M4）：** 约 2～4 周；阶段 15/16 另计；随机训练详设另计。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 漏改接口导致串数据 | 统一查询助手强制 `user_id`；越权集成测试 |
| 迁移丢数据 | 先 `pg_dump`；归属策略写进迁移注释 |
| Cookie 本地跨域 | Vite 代理同站或明确 SameSite |
| localStorage 串号 | key 带 userId；退出清理 |
| 「永久登录」难吊销 | Refresh 落库 + 登出/改密吊销；永久仍设实际上限 |
| 随机训练与复盘会话概念混淆 | 先写清模式差异再定表；勿过早绑死 |

## 10. 第一期 Definition of Done（多用户）

- [ ] 可注册或开户、登录、退出；未登录无法使用业务 API
- [ ] 登录可选 1 天 / 7 天 / 30 天 / 半年 / 永久（Refresh）
- [ ] 至少两用户：自选 / 复盘 / 买卖 / 笔记 / 统计互不可见
- [ ] 历史单租户数据已归属首用户或已确认清空
- [ ] 行情仍共享
- [ ] 越权返回 403/404（策略统一）
- [ ] 环境变量、迁移、开户方式有文档
- [ ] （可选并行）随机训练：仅完成需求备忘 / 表草案，不强制上线玩法
